# 当前观测基线

本阶段实现一个可运行的零样本视觉语言模型基线：输入任务指令和当前单张图像，输出阶段、失败判断、可见证据及需要时的两层纠错建议。诊断正确性仍需人工核对和评测。

## 方法与边界

- 模型：[官方 Qwen3-VL-2B-Instruct](https://huggingface.co/Qwen/Qwen3-VL-2B-Instruct)，版本固定为 `89644892e4d85e24eaac8bacfd4f463576704203`，权重文件约3.96 GiB。
- 框架：Transformers 4.57.6、PyTorch 2.11.0；使用SDPA，不依赖FlashAttention或bitsandbytes。
- 输入：`task_instruction` 和 `observation.images.cam_high` 的当前画面；最长边512像素、处理器像素上限196608。
- 每次推理重新构造消息，不包含历史图像、状态向量、动作目标、失败标签、关键帧或纠错标注。帧编号/时间只用于日志，不作为模型提示。
- 固定采样：每100帧一次，在25 FPS数据上间隔4秒。默认两条轨迹最多9次调用，没有按失败关键帧选样。
- 模型生成最多512 tokens，使用贪心解码。通过LM Format Enforcer约束JSON结构，并检查字段与状态的一致性。
- 两层建议用于离线观察和研究记录，不连接机器人控制接口。

## 判断约定

| status | failure | 含义 |
| --- | --- | --- |
| `in_progress` | `false` | 根据当前画面判断任务正在进行，尚未确认失败；不表示整段任务成功 |
| `failure` | `true` | 模型认为当前有可见失败证据，必须同时给出两层建议 |
| `completed` | `false` | 模型认为全部目标的完成条件可见，必须给出证据；需要人工核对 |
| `insufficient_evidence` | `null` | 当前画面不足以判定，继续观察 |

单张图像通常无法证明持续夹持、物体是否随末端移动或动作顺序，也难以区分动作还在尝试与已失败。提示明确要求避免据此编造结论。没有用整段轨迹的成功/失败标签代替逐时刻判断。

`stage` 取 `approaching/grasping/transporting/manipulating/placing/completed/unknown`。失败证据必须非空；失败时 `high_level_advice` 描述恢复子目标，`low_level_advice` 包含 `action/reference_frame/completion_check`，要求两层对应。

当前输入没有标定的3D坐标或末端力矩，因此低层建议的参考坐标系只允许 `image/not_applicable/unknown`。图像中的左右方向不自动转成机器人基坐标系。

结构校验只检查格式、状态关系和字段完整性；不保证模型描述的事实、任务阶段或建议正确。错误JSON与不一致结果保留原文，`result_valid=false`、`result=null`，不会补写成某个诊断。所有结果无效时程序报错。

## 环境与模型准备

本机已建好独立的 `cv-baseline`，原 `cv-streaming` 不变。其他电脑可以从已建立的输入环境克隆：

```bat
conda create -n cv-baseline --clone cv-streaming -y
conda activate cv-baseline
python -m pip install -r requirements-baseline.txt
python download_baseline_model.py
```

新环境也可通过 `environment-baseline.yml` 建立，再安装同一依赖。requirements-baseline.txt中的PyTorch来源适用于已验证的Windows/NVIDIA配置；其他平台应选择相应PyTorch构建。完整开发环境版本记录在 `requirements-baseline-lock.txt`。

下载需要代理时为下载命令显式添加 `--proxy http://127.0.0.1:7897`，代理地址按本机调整。文件大小与官方大文件SHA256经过检查，来源与哈希保存在 `models/Qwen3-VL-2B-Instruct/model_manifest.json`；权重不提交Git。推理仅从本地加载，不信任或执行远程模型代码。

## 运行

默认在GPU上运行两条轨迹的9个固定采样点：

```bat
conda activate cv-baseline
python run_current_observation.py
```

只验证一个GPU输入时：

```bat
python run_current_observation.py --max-model-calls 1
```

CPU可显式用于流程调试；这类结果单独记为功能验证，不作为GPU性能实验：

```bat
python run_current_observation.py --device cpu --max-model-calls 1
```

`configs/current_observation.yaml` 固定相机、采样间隔、模型和预算。CLI覆盖会保存在本次 `config.json` 中，不修改源配置。CPU使用float32及8个线程，速度低于空闲GPU，内存需求也更高；GPU使用BF16。

启动GPU模型前至少需要5000 MiB可用显存，每次生成前至少留1024 MiB余量。显存不足时每10秒检查一次并暂停等待；没有等待超时，也不自动切换CPU或结束其他程序。若已加载权重，会先将权重暂存到内存并释放本基线显存，显存恢复后重新放回GPU。内存暂存不执行CPU推理。

2026-10-15 补充 Windows 物理显存检查：按 GPU UUID 对齐 `nvidia-smi` 与 CUDA 的报告，取较小的空闲量，避免 CUDA 报告偏高时错误放行。无法核实物理显存时明确报错。新加入的有限历史监测入口使用6500 MiB启动/恢复门槛，当前观测基线仍使用上述5000 MiB配置。

若另一任务在检查后占用了显存，导致加载或生成时CUDA显存耗尽，会释放本次尝试，等待后在GPU上重试同一当前输入。重试不读取后续帧。所配置的显存门槛如果高于GPU总容量会明确报错，需要调整模型/输入预算；等待不能增加物理容量。

每次生成有120秒软时间预算，在生成步之间检查；不是对运行中单步的硬中断保证。资源等待不消耗该次生成预算。截断或超时导致的不完整输出仍会记为无效结果。

## 输出与复现

运行目录：`output/baseline_runs/<时间>/`。

| 文件 | 内容 |
| --- | --- |
| `images/` | 实际提交给模型的缩放后RGB图像 |
| `predictions.jsonl` | 原始响应、校验后结果、错误信息、提醒标志、耗时和令牌/显存记录 |
| `config.json` | 包含CLI覆盖的实际参数 |
| `prompt.txt`、`output_schema.json` | 固定提示与JSON约束 |
| `provenance.json` | 模型/数据版本、依赖版本、提示哈希及实际使用的模态 |
| `summary.json` | 调用数量、有效/无效输出、读取覆盖范围和运行状态 |

`alert=true` 仅表示本次有效结果判为失败。无效输出或证据不足时不会发提醒，不能将未提醒当作没有失败。本基线逐次判断，尚未实现重复提醒抑制。

`inference_ms` 记录成功尝试的预处理、约束解码和生成耗时；资源等待（`gpu_wait_time_s`）、权重移出/恢复（`gpu_resume_time_s`）和显存耗尽的失败尝试（`oom_retry_time_s`、`oom_retries`）分别记录。启动等待在provenance中单独记录，模型加载耗时排除这段等待。实际总运行时间包含以上开销。

这些耗时不是相对首次可检测时刻的提醒延迟。当前回放是顺序离线试验，不宣称可持续跟上25 FPS输入。

测试命令：

```bat
python -m unittest discover -s tests -v
python verify_current_observation.py
```

原输入环境也能运行基本测试；缺少可选约束解码依赖时，相关两项测试会跳过。

此前在CPU上完成9次固定采样，9条输出均通过结构/状态检查，平均调用耗时约27.2秒。该记录只用于功能验证，单独保存在 `docs/current-observation-functional-validation.json`。正式基线默认GPU运行，验证记录为 `docs/current-observation-validation.json`，二者不混算速度。实际提交图像会逐张与当前源帧校验，结果也与原始模型响应核对。

显存空闲后，GPU已完整运行同样9个采样点，9条均通过结构/状态检查，两个数据源的819帧也完整顺序读取。此次GPU平均调用耗时约5.1秒，PyTorch分配显存峰值约4239 MiB（4.14 GiB），总运行时间约68秒；这仅是本机小样例测量，包含约束解码，尚非完整性能评测。

等待机制覆盖启动检查、运行前检查以及加载/生成时CUDA显存耗尽；测试模拟显存不足后恢复、释放权重与原输入重试。此次GPU运行无资源等待，不代表并发任务永远不会造成等待。

此次GPU和此前CPU结果均大多判为 `approaching`，失败轨迹的3个采样点没有提醒。样例说明基线流程已可运行，也显示了单帧小模型的阶段区分和失败识别限制；尚无人工首次可检测时刻标注，未据此计算Recall或F1。
