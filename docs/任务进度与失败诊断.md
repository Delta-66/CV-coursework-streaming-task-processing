## 模型实际得到什么

`temporal_diagnosis.py` 在每条 episode 内维护有限窗口。默认 `history_size: 2`、`max_history_s: 8`，最多两张过去的采样图与当前图；超出时间或容量即丢弃，episode 切换清空。模型每次收到新构造的消息，不收到之前的模型回答。

| 输入 | 处理方式 |
| --- | --- |
| 任务指令 | 原数据指令 |
| 图像 | `cam_high`，最大边384像素，保留实际输入 PNG |
| 历史 | 仅已经读到、时间不晚于当前的采样帧 |
| 关节状态 | 白名单读取14维 state/qpos、velocity/qvel、effort，保留源字段名和数值 |
| 夹爪 | 从 qpos/state 的第6、13号索引提取原值（从0开始）；不擅自解释为已抓住物体 |
| 缺失模态 | 保持缺失，不伪造末端位姿或力/力矩测量 |

模型不读取 `recorded_targets`、`extra_records`、整段失败标签、纠错关键帧标注。`action_eef` 是动作目标，不能当作实际末端状态；effort 不能当作六维力/力矩传感器。当前默认是图像和关节信息，没有深度/多相机融合；原有输入接口仍支持这些数据。

## 输出与提醒

模型回答含12个字段：

| 字段 | 含义 |
| --- | --- |
| `stage`、`status`、`failure` | 当前阶段、执行状态及是否观察到失败；不确定时 `failure=null` |
| `key_states` | `grasp`、`target_relation`、`task_goal`，各自允许 `unknown` |
| `expected_effect`、`observed_effect` | 当前动作的预期效果及可观察变化 |
| `action_outcome` | `achieved` / `not_achieved` / `uncertain`；动作成功不等同于整个任务完成 |
| `failure_type` | 抓空、掉落、放置失败、受阻、任务偏离或其他 |
| `evidence`、`evidence_frame_indices` | 简短可核查描述及本次实际输入的帧号 |
| `high_level_advice`、`low_level_advice` | 失败时的恢复子目标和相应建议；仅建议，不发送机器人控制命令 |

输出由 JSON 约束解码与有限的字段一致性规则共同校验：失败必须有明确类型、`not_achieved`、过去及当前图的引用；完成必须有当前证据与 `task_goal=met`。未来、未输入或重复帧号，以及违反这些显式规则的字段组合会被拒绝。检查尚不能识别所有语义矛盾，例如“拿刀已达成”与“未持有刀”的冲突。原始回答照常保存，校验失败不会伪装成成功或失败。

`diagnostic_tracking.py` 将模型回答转为可审计的跟踪结果：

1. 阶段和每个关键状态分别需要连续两次支持才确认。未知/无效结果中断候选；旧值保留，但标为 `stage_stale` 或 `key_state_stale`，不能理解成当前已确定。
2. 同类失败需要连续两次合格证据才提醒。未恢复的同类事件只提醒一次；类型切换后又切回也不重复提醒。
3. 不确定或普通“进行中”不会解除已有故障。恢复需要连续两次当前证据、动作效果 `achieved`，且关键状态匹配全部未恢复问题：抓空/掉落要求当前已持有物体，放置失败要求已到目标位置；受阻、偏离及其他类型保守要求任务目标已满足。
4. 恢复后出现的新事件允许重新提醒。不同事件间默认冷却8秒，按数据时间计算；到期仍需当前支持，不会仅因计时结束自行发出提醒。

这些是未校准的启发式策略，模型重复同一误判仍可能触发误报。严格确认也可能增加漏报或延迟。最早在第3个采样点才能满足“历史比较＋连续两次失败”，当前常规采样约为轨迹开始2秒；强制尾帧可能使第3次略提前。实际可检测时刻需要人工标注，采样间隔内的短暂故障仍可能被跳过。

### 第2步的实质缺口

| 缺口 | 已观察到的证据 | 应补充的判断依据 |
| --- | --- | --- |
| 动作达成条件没有结构化 | episode 0 / frame 0 的预期为拿刀，`grasp=not_held`，却输出 `action_outcome=achieved`，仍通过当前校验 | 将任务子步骤与可检查条件绑定，例如“目标刀已被持有”；字符串非空、枚举合法不能证明效果达成 |
| 通用阶段缺少子任务身份 | `approaching` 不能区分去刀架拿刀与切完后归还刀 | 记录当前子任务、目标对象、目标位置、已完成步骤和前置条件；不把离线整段标注直接送给当前测试样例 |
| 证据引用未证明视觉事实 | 两次模型断言可能重复同一误判；帧号有效只证明输入可用 | 区分可观察事实、原因假设与不确定性；为阶段、关键状态和失败建立独立人工标注 |
| 提醒事件缺少对象绑定 | 当前按 `failure_type` 合并事件，`grasp=held` 不区分是否拿到原目标 | 事件需绑定子任务和作用对象；解除故障需验证该事件对应条件 |
| 原粗采样与确认规则不匹配 | 原9次配置每100帧采样，失败需过去＋当前证据并连续两次支持，最早第3个采样点才能报警 | 本轮已改为每25帧＋尾帧；仍需在开发/验证集比较证据门槛及延迟，不能通过关闭提醒来降低误报 |
| 当前失败分类与官方标签不同 | 当前 `grasp_miss` 等偏向现象，官方有任务规划、夹爪位姿、夹爪状态、人为干预等类别 | 分开记录失败现象与原因；定义有依据的标签映射，无法对应时明确未知 |

对完整元数据统计：5,202条轨迹中有 **2,183条（41.96%）长度不超过200帧**，其中2,088条为失败轨迹、95条为成功轨迹。它们在原每100帧采样且不补末帧的配置下最多只有 frame 0、100 两个观测，无法满足三采样点的最早提醒条件。这个统计描述本轮修改前的配置限制，不是当前25帧＋尾帧协议的覆盖率，也不是测得的模型漏报率。

### 第3步倒推第2步需要交付什么

第三步要求高层规划调整与低层执行调整保持一致。第2步应先提供能支撑两层建议的状态依据：

| 第3步需要回答 | 第2步应提供 |
| --- | --- |
| 下一步应该做什么、为什么 | 当前子任务、哪些前置条件未满足、失败影响哪些后续步骤 |
| 应重试、回退还是换策略 | 已尝试的动作、预期效果、实际效果、可观察问题与原因假设 |
| 具体动哪个对象、哪个方向 | 作用对象、可用的空间关系、坐标系及标定能力；不把图像方向冒充机器人基座方向 |
| 完成后如何检查 | 与该子任务和目标对象绑定的达成/恢复条件，能在后续输入中核验 |

现有 `high_level_advice`、`low_level_advice`、`completion_check` 只是基础输出字段，其文本一致性和可执行性未完成验证，不能算第3步完成。本次复审不扩展第三步实现。

### 后续验收顺序

1. 固定真实轨迹的开发、验证和独立测试归属，同一轨迹的相机、格式、帧、窗口和派生VQA不得跨集合。
2. 在选定任务的开发集上定义子任务、目标对象和达成条件；使用官方标签辅助离线审阅，人工补充逐时刻阶段、关键状态和首次可检测证据。
3. 在验证集校准采样、确认、去重与恢复策略。每项改动同时检查误报、漏报、重复提醒和延迟，记录未知/拒答比例。
4. 冻结提示词、模型、模态和参数后，才运行独立测试。报告实际评估的轨迹/时刻数、失败检出率、成功轨迹误报率、重复提醒以及源时间/计算时间两类延迟。
5. 当第2步能提供可核查的子任务与失败依据后，再实现第三步两层纠错。是否微调模型由验证集证据和资源评估决定，划分数据不意味着已经训练。
