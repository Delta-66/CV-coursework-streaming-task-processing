# 空闲时运行完整时序测试

适用项目：`C:\Users\lenovo\Desktop\CV`；现有环境：`cv-baseline`。

## 本次决定

**当前不启动500条全量测试，也不保留等待显存后自动启动的后台任务。** 用户要求同时满足“约5 GiB显存能运行”和“预计5小时内完成”。省显存实验已在5 GiB预算下完成两个开发轨迹，但估计全量纯推理约17.6小时，时间条件不满足；现有正式配置本身也未通过5 GiB资源测试。

这里运行的是 **Qwen3-VL-2B-Instruct预训练模型的推理评测**，不更新权重，不是模型训练。本项目尚无微调训练入口。后续要训练时，应使用已划分的训练/验证集制定独立方案，不能拿测试集调参。

本次“全量测试”指官方检测子集全部500条轨迹：128,611帧，5,850次判断。不是把5,202条数据全部混在一起跑；训练预留3,754条、验证939条、已阅开发3条、测试保留506条（500条检测＋6条额外媒体引用）仍保持独立。

## 显存与耗时依据

2026-10-16使用真实已阅开发轨迹测试，未读测试集输出：原配置在5,120 MiB（5 GiB）PyTorch分配上限下，episode 0的首帧成功，第二个判断时刻（frame 25，两张图）发生CUDA OOM，随即退出。不能只把正式配置的启动门槛改小就认为能运行。

随后保持模型权重、BF16精度、三帧窗口、图像分辨率和提示词不变，实验切换为memory-efficient SDPA及显式KV复制。资源验证结果如下，完整数据见 [资源检查记录](temporal-resource-check.json)：

| 项目 | 省显存实验结果 |
| --- | --- |
| 数据范围 | 已阅episode 0、18，819帧完整顺序读取，两条末帧均覆盖 |
| 判断次数 | 35次全部完成，均通过现有输出校验 |
| PyTorch分配上限 | 5,120 MiB（5 GiB） |
| PyTorch分配峰值 / 预留峰值 | 4,627 / 4,882 MiB |
| 本进程专用显存采样峰值 | 5,005 MiB，约4.89 GiB |
| 本进程共享显存采样峰值 | 78 MiB |
| 平均推理耗时 | 10.90秒/次 |
| 本次实验总耗时 | 约6.75分钟，含加载和记录 |
| 500条估算纯推理耗时 | 约17.6小时；按单图/两图/三图窗口比例加权 |

输入已重新核对：35个计划时刻、99次窗口图像引用、状态原值与源数据一致。资源实验没有评估判断的视觉正确性，也没有运行500条测试。实验开始时物理空闲约6,077 MiB，通过分配器上限控制PyTorch预算，再另外采样总进程显存；没有把系统物理空闲显存硬限制为5 GiB。两条轨迹不能保证其他任务、更长输出和资源竞争下也一定不超限。

5小时内完成要求平均每次低于约3.08秒，还未计其他开销。此次实验估算17.6小时，多预留20%约21.1小时；下载、显存等待及其他任务的输出长度仍可能进一步延长运行。**现有正式入口仍使用原实现**，依据此前9次开发判断的11.46秒/次，估计纯推理约18.6小时。两项都是开发样例估算，不是完整测试的实测耗时。

整个数据集按顺序处理，每次只送入当前图和最多两张历史图；增加轨迹数量主要增加运行时间、磁盘记录，不会把全部视频同时装进显存。正式入口目前仍使用原注意力实现，启动/恢复门槛为 **6,500 MiB空闲专用显存**；原开发记录的PyTorch分配峰值约6,166 MiB、预留峰值约6,850 MiB，因此仍需运行时监测，并不能保证刚好达到门槛就永不OOM。

资源探测脚本 `probe_temporal_resources.py` 另提供进程内的省显存注意力实验。该选项尚未并入冻结的正式评测入口；不要把探测脚本成功当作正式500条评测已完成，也不要修改旧结果的协议文件来混用配置。

显存口径：1 GiB＝1,024 MiB；5 GiB约为5.37 GB。探测脚本限制的是PyTorch缓存分配器，CUDA上下文等额外占用不包含在该上限内，并另行采样Windows的本进程专用/共享显存。约1秒一次的计数器采样可能漏掉瞬间峰值。依据：[PyTorch分配器上限说明](https://docs.pytorch.org/docs/2.11/generated/torch.cuda.memory.set_per_process_memory_fraction.html)。不同注意力内核可能产生数值差异，需要独立记录配置与评测，见[PyTorch SDPA说明](https://docs.pytorch.org/docs/2.11/generated/torch.nn.functional.scaled_dot_product_attention.html)。

## 本机启动方法

等到愿意让电脑长时间运行、且显存有余量时，在VS Code打开整个 `C:\Users\lenovo\Desktop\CV` 文件夹，打开PowerShell终端。以下命令直接指定已有解释器，不依赖终端是否自动激活环境：

```powershell
Set-Location 'C:\Users\lenovo\Desktop\CV'
$cvPython = 'C:\Users\lenovo\.conda\envs\cv-baseline\python.exe'
& $cvPython -c "import sys, torch; print(sys.executable); print('CUDA:', torch.cuda.is_available())"
nvidia-smi --query-gpu=name,memory.total,memory.used,memory.free --format=csv
```

应显示 `cv-baseline\python.exe` 和 `CUDA: True`。看 `memory.free` 的专用显存余量，不把任务管理器中的共享系统内存当作额外显存。现有正式入口空闲不足6,500 MiB时会等待；若始终只有约5 GiB空闲，暂不执行下面的正式运行命令，省显存方案需要另行接入并冻结新协议。无需安装/删除任何已有Conda环境。

先检查冻结计划（不加载模型、不运行推理）：

```powershell
& $cvPython run_temporal_benchmark.py --plan-only
```

核对输出 `episode_count: 500`、`total_frames: 128611`、`total_model_calls: 5850`。准备约1.1 GB数据下载空间，另外给输入图像与预测记录留出空间；不下载其他相机或整套原始HDF5。

开始完整测试或恢复上一次运行：

```powershell
& $cvPython -u run_temporal_benchmark.py --download
```

如果下载必须经过本机代理，且该代理正在运行，则使用：

```powershell
& $cvPython -u run_temporal_benchmark.py --download --proxy http://127.0.0.1:7897
```

代理端口按本机实际设置填写；无须更改全局网络配置。文件按轨迹下载并核对版本/哈希，已核验文件复用。

也可在VS Code的“运行和调试”选择“完整时序评测：500条轨迹（GPU，可续跑）”，使用 `Ctrl+F5`。解释器应选择 `cv-baseline`；只启动一个评测进程。插电运行，并根据需要在Windows设置中临时关闭自动睡眠，运行完恢复原设置。

## 查看进度、中断与继续

在另一个终端执行完整命令，避免依赖前一终端的变量：

```powershell
Set-Location 'C:\Users\lenovo\Desktop\CV'
& 'C:\Users\lenovo\.conda\envs\cv-baseline\python.exe' run_temporal_benchmark.py --status
```

结果目录：`C:\Users\lenovo\Desktop\CV\output\temporal_benchmark\canonical_detection_v1`。

| 文件/目录 | 用途 |
| --- | --- |
| `progress.json` / `checkpoint.json` | 完成轨迹数、完成判断数、当前轨迹与状态 |
| `episodes/` | 逐轨迹输入图像、原始模型回答、状态跟踪与提醒 |
| `evaluation.json` | 离线汇总结果，区分中间结果和完整结果 |
| `protocol.json` / `plan.json` | 冻结版本、参数、代码哈希及全部计划时刻 |

需要用电脑时，在运行终端按一次 `Ctrl+C`，等待返回命令提示符。下次执行同一个启动命令即可：已核验完整轨迹跳过，当前中断轨迹从头重跑，保证历史窗口和提醒状态一致。允许分多个空闲时段完成，不要求一次连续跑完18.6小时。

运行中显存不足会释放GPU权重、等待空闲后重试同一个输入，推理仍使用GPU。等待时间会延长总耗时。CPU暂存权重不等于用CPU执行模型。

不要删除检查点、手改协议哈希或改动同一批次的提示词/采样规则。若确实更新程序或参数，使用独立的新结果目录重新冻结计划，例如 `--run-dir output/temporal_benchmark/canonical_detection_v2`；新批次不会沿用旧批次的完成计数。

## 完成与检查结果

完整执行应覆盖500条、5,850个计划判断时刻，包括每条末帧。查看失败轨迹、无效输出等计数，不能只看到程序退出就认定成功。未运行和中断的轨迹不是“未发现故障”。全量入口结束时会自动汇总；也可手动重新计算：

```powershell
& 'C:\Users\lenovo\.conda\envs\cv-baseline\python.exe' evaluate_temporal_benchmark.py --benchmark-dir output/temporal_benchmark/canonical_detection_v1
```

检查 `evaluation.json` 的状态、实际纳入/排除数量、失败轨迹检出率、成功轨迹误报率、无效输出比例和提醒记录。整段官方结果只能评价轨迹级检测；阶段准确率和首次可检测延迟仍需要独立时序标注。跑完这一轮不等于第二步已经达标，第三步暂缓实现。
