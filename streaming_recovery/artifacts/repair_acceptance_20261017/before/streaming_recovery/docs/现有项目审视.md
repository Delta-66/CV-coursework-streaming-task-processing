# 现有项目审视与本次接入边界

本次先独立完成需求与数据核查，再只读检查原实现。没有将原模块的存在视为需求已满足，也没有修改原文件或已有变量。新工作全部放在 `streaming_recovery/`。

## 已经有用且经过检查的基础

- 原项目已有 LeRobot/HDF5 适配、字段角色分类、多相机时间戳校验和原始数据/模型下载来源；数据可直接复用。
- `current_observation.py` 的请求只含当前图像和指令；`temporal_diagnosis.py` 的 `measured_states` 有实测状态允许列表，`CausalWindow` 限制历史帧和时间；模型消息构造未把轨迹路径/标签加入提示。不能据源数据有标签就断言原监测器已经泄漏答案。
- 原 `diagnostic_tracking.py` 有连续证据确认、有限类型事件记录和重复提醒抑制；不把它描述成完全没有事件机制。
- 原项目的验证说明对“启动检查”与“识别效果”有明确区分。已有 `docs/task-monitor-validation.json` 记录 9 次有效模型输出、0 次提醒，并明确未证明漏报或识别效果。
- 本轮实际运行原 `tests/`：**113 项全部通过**，未修改原测试。初次运行因沙箱系统临时目录权限产生 81 个错误；把该测试进程的临时目录设置到新工作区后重跑通过。两个原始测试日志均保留，不能将权限失败当成算法失败，也不能只引用最终通过而隐去环境修复。

| 发现 | 证据与影响 | 新实现处理 |

| 建议校验主要保证结构 | `current_observation.py:92` 校验非空字段和坐标枚举；实际探针中“高层恢复抓取，低层继续切割并写机器人基座 -0.1 m，但 reference_frame=image”仍通过 | 由同一诊断生成受约束的下一动作；共享目标/事件/对象 ID；禁止无来源数值、检查前置/后置条件 |

## 本轮方案取舍

本地 Qwen 能真实加载和产生回答，但本轮两种提示的 34 次实际调用均没有产生可用于严格契约验收的有效结果。第一轮是刀架位置/共同运动等语义矛盾；第二轮有缺字段和关系混乱。原始输出保留在两份 probe JSONL。不能据“有权重且能生成 JSON”宣称视觉诊断可靠，也不能借此断言另一套提示或原项目的模型调用必然同样失败。

主路线因此选用明确场景假设的经典视觉模型：首帧参考、颜色/形状分割、运动关联；这牺牲泛化范围，换取当前数据上真实可运行、可核查的取刀效果判断。对完整切割任务的剩余阶段保留未知，而不是编造完成。当前两个例子也是开发样例，不构成独立测试集成绩。
